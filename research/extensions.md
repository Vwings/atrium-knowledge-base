# 扩展机制

## 状态

汇总插件机制的讨论结论和候选设计。已确认结论按主题汇总在 [README](../README.md)。

## 结论

**已确认（2026-10-20）**：设计一个通用的插件机制，不局限于工作流；工作流是其中一个扩展点。插件机制从一开始就按通用方式设计；首期交付哪些扩展点，划 MVP 时再定。

## 通用机制需要回答的问题

**候选**：

| 问题 | 说明 |
| --- | --- |
| 声明 | 插件声明自己为哪些扩展点提供内容、自身版本、依赖的核心版本 |
| 发现与启用 | 安装、发现、启用、停用；停用后能卸载干净 |
| 边界 | 官方工作流包也是普通插件，可以停用替换；但一个插件不能悄悄改变其他插件或核心的行为；不直接写核心状态，只通过核心操作 |
| 权限 | 插件能读什么、能执行哪些有副作用的操作，由用户授权 |
| 版本 | 进行中的任务绑定开始时的插件版本；插件升级时有迁移办法 |
| 冲突 | 多个插件为同一扩展点提供同类内容时如何选择 |

## 候选扩展点

- **工作流**（已确认；默认工作流以官方工作流包提供，产物类型如 spec、Review 由工作流声明）：一类任务的步骤、闸门和完成条件，见[任务与工作流](task-and-workflow.md)。
- **空间组合规则**：哪类任务需要带哪些项目。2026-10-20 已确认这属于团队规则或扩展，不进核心。
- **项目来源**：在裸仓库池、共享目录池之外接入其他来源，例如内部代码平台。
- **上下文生成**：`AGENTS.md`、编辑器工作区文件的模板，或适配其他 Agent 与编辑器。
- **确认策略**：按仓库、目录或产物类型配置确认强度。
- **Agent 工具与界面视图**：为内置 Agent 增加工具，为桌面端增加视图。

## 参考

- 现行 Atrium Skill 的扩展包机制已回答一部分：`atrium-ext-` 前缀发现、`<扩展名>/<名称>` 命名、只补充不覆盖、声明表与按需加载、缺失即报错。但它是文字规则加校验器，没有程序层的注册、版本和能力协商；`workflow_file` 依赖安装路径，产品宜改用稳定标识和版本。以上为 2026-10 的核对结果。
- Codex 的能力协商与实验接口、OpenCode 的插件生命周期与可重算派生状态、Pi Chord 的依赖图与 Facet，见[程序架构参考](reference-architectures.md)。
