# Agent 与入口

## 状态

汇总入口（桌面、CLI、外部 Agent、内置 Agent）与 Agent 职责的讨论结论和候选设计。已确认结论的原话与日期另汇总在 [README](../README.md)。部署形态和技术参考见[程序架构参考](reference-architectures.md)。

## 基础定位

**已确认（2026-09-22）**：

> Atrium 是一套用于组织工作空间、管理任务和支持可插拔工作流的产品，以程序维护结构化状态，并提供相应的操作与可视化能力。

CLI 和桌面端是 Atrium 拟开发的产品组成；Codex 等外部 Agent 是使用方。没有 Agent 时，核心管理操作也应能独立执行。2026-10-20 用户重述的三大能力（上下文环境、任务状态、工作流）是这一定位的展开，见[产品全貌草案](product-overview-draft.md)。

为后续设计保留的原则（候选，接口和实现待设计）：

- 业务操作独立于界面，CLI、桌面和 Agent 使用相同的核心能力。
- 状态和业务校验由核心维护，Agent 通过操作接口提出请求，不直接改数据库、Markdown 或状态投影。
- 任务、工作流与 Agent 对话分别管理生命周期，关闭对话不等于结束任务。
- 耗时操作的进度和结果可独立查询，不依赖某个窗口或一次调用始终连接。

## 桌面与 CLI 形态

**已确认（2026-09-23）**：

- 桌面端围绕空间、任务和工作流提供图形操作及 Agent 自然语言交互；方案和实际结果在业务视图中呈现。
- CLI 提供不依赖 Agent 的确定性命令，供用户、脚本和外部 Agent 调用；同时考虑提供交互式 Agent 模式。
- 桌面与 CLI 的自然语言入口复用领域工具、规则等 Agent 能力；所有入口共享核心状态与业务操作。复用不等于必须同一进程，也不预设对话自动共享。
- 外部编码 Agent 通常通过确定性接口使用 Atrium，不要求每次调用都经过 Atrium 的模型推理。现有使用关系可以抽象为 `Codex → Atrium Skill → Atrium CLI`：Skill 指导 Agent 何时使用 Atrium，CLI 或公共接口执行确定性操作。

交付顺序、Agent runtime、模型、进程、命令语法、存储和 UI 布局仍未确定。

**候选**：确定操作需要不经过 Agent 的快速通道（界面、CLI），Agent 处理意图模糊的请求。需要避免：简单动作也强制对话；每个项目或步骤都要求重复确认；Agent 修改覆盖人工调整；图形界面与对话维护两份不一致的状态；在领域场景未验证时扩大为通用编码工具或通用 Agent 平台。

## Agent 接入

**已确认（2026-10-20）**：Agent 接入（Agent 如何发现并可靠使用 Atrium）作为贯穿问题，与入口、状态与操作接口、授权护栏并列。

**候选**：Agent 进入空间时，要能可靠地知道这是 Atrium 空间、当前任务是什么、该通过什么接口操作，而不依赖 Agent 是否“记得”加载某段规则。依据：现行 Skill 靠模型匹配描述来加载入口，匹配失败时整套规则静默失效，用户和 Agent 都察觉不到。

## 内置 Agent

**已确认（2026-09-23）**：Agent 从初期参与完整产品体验设计，不预设内置 Agent 必须后做；具体交付顺序另定。只有接口兼容不足以回应“减少点击、减少手写说明”的诉求。

**候选**：用户在桌面端输入“帮我建个工作空间……”，由内置 Agent 理解意图、生成计划并调用与 CLI、外部 Agent 相同的核心接口。

```text
内置 Agent
  → 意图理解、计划生成、澄清
  → Atrium 核心命令 / 查询接口
  → 空间 / 任务 / 工作流结构化状态
```

- Agent 可以是桌面端内嵌的本地运行时，也可以由桌面端拉起 sidecar；是否使用 Pi 或其他 runtime 未定。
- 所有变更都经过带 schema、权限、冲突检查和幂等语义的核心命令。
- 内置 Agent 可以使用内部的工具定义，也可以复用面向外部 Agent 的协议，不要求存在外部 Skill 文件调用链。

**候选**：架构初期就需要的 Agent 兼容边界：

1. 意图与计划分离：Agent 提出资源组合和操作计划，核心负责解析、校验和执行。
2. 预览与执行分离：有副作用的动作可以先生成计划和差异。
3. 结构化事实与自然语言说明分离：路径、版本、来源、角色和执行结果由程序维护；Agent 生成的简介带草案或确认状态。
4. 稳定的查询、错误和进度接口：所有入口读取同一事实。
5. Agent 可替换：核心不依赖某个模型供应商、Pi 或特定对话协议。

缺少这些边界，后期加入 Agent 时容易出现：UI 表单直接触发副作用，Agent 无法复用；核心只提供面向按钮的专用操作；项目简介缺少草稿和来源字段；创建过程没有幂等、进度和部分失败语义，Agent 无法安全重试；任务、工作流、对话和执行混在一起，牵动状态模型。

## Agent 职责

**候选**：Atrium 可以呈现为面向研发组织工作的领域 Agent：围绕空间准备、项目组织、任务状态和工作流协调持续提供能力。领域上下文、工具、操作规则和结果校验共同构成专门能力，不需要训练专用模型，也不是每个事项一个 Agent。结构化核心能校验路径、资源、状态和操作条件，但不能证明 Agent 的语义理解永远正确。

| 场景 | Agent 候选职责 | 核心程序提供的依据与操作 |
| --- | --- | --- |
| 创建空间 | 根据目标查找项目，澄清版本，提出组合与简介 | 来源查询、方案校验、资源创建及验证 |
| 日常调整 | 理解添加、替换或移除意图，说明影响 | 成员与依赖检查、变更执行、实际状态查询 |
| 任务推进 | 整理目标、推荐工作流、解释阻塞、建议下一步 | 任务状态、步骤条件、证据引用和允许的状态变更 |
| 跨空间拆分 | 建议迁移哪些任务和资料，保留哪些共享入口 | 归属与冲突检查、迁移记录、引用校验和恢复 |
| 回收空间 | 汇总未完成任务与未保留成果，提出处置方案 | 资源归属及工作目录检查、授权范围内的回收 |

**已确认（2026-10-20）**：内置 Agent 只做组织类工作：建空间、登记和管理任务、推进流程。业务编码交给 Claude Code、Codex 等外部 Agent；调度外部 Agent 暂不做，等有明确场景再讨论。

## Agent 开发与语言路线

**候选**：Agent 开发可以复用现有模型，通过运行时循环组织：接收目标与上下文 → 请求模型回答或提出工具调用 → 程序校验工具名、参数和授权并执行 → 把实际结果返回模型 → 继续、澄清或结束。Atrium 需要自建的是领域能力（项目和空间查询、资料读取、方案草拟、资源操作、任务及工作流接口、与界面同步），以及对话持久化、上下文选择、取消、网络失败、成本和效果评估等运行问题。

核心语言与 Agent 运行时语言可以分别选择。候选路线：Rust 核心加 Rust Agent 运行时；Rust 核心加 TypeScript Agent 运行时；主要用 TypeScript。混合路线能复用其他语言的运行时，但引入进程通信、打包和版本协调成本。不能因为选了 Rust CLI 就推出 Agent 必须用 Rust，也不能因为考虑 Pi 就认定整个产品改用 JS。

架构顺序：先明确业务职责、状态归属和入口关系，同时检查影响可行性的技术问题；领域职责稳定后再比较运行时、语言、进程通信和部署组合。建议之后用一条代表性场景验证候选运行时：读取真实资源、形成可编辑计划、澄清歧义、通过核心执行、反馈结果、处理中断和部分失败。尚未开始。
