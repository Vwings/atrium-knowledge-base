## 一句话定位

**草案**：Atrium 为 AI 开发中的每个任务准备并持续维护它的工作环境：在哪做（上下文环境）、做到哪（任务状态）、怎么做（工作流），让人和 Agent 都能直接接手。

## 要解决的问题

**已确认（用户陈述）**，表述由 Agent 整理：

1. **Agent 能看到什么，取决于打开的文件夹。** 用 AI 开发，第一件事是打开一个文件夹。文件夹里有什么，直接决定 Agent 能看到什么；Agent 可以自己去找，但效果不如东西就在眼前。复杂任务往往涉及多个 Git 仓库，单个仓库目录描述不了一件事。`/add-dir` 之类的命令只是临时补充，也不好用。人同样需要在编辑器里看到这件事涉及的项目。
2. **大任务做不完一个会话。** 会话结束或上下文压缩后，目标、决策和进度要能保留下来，新会话能接着做。
3. **任务要按有效的流程执行。** 光有进度不够，还要按规范的流程推进；不同公司可能有自己的专属流程。

**草案**：三个问题的共同点是，这些东西现在都要靠人手工准备，或者靠 Agent 按提示词自觉维护，成本高、结果不稳定。

## 目标用户

**已确认（2026-10-20）**：不按个人或团队区分。Atrium 服务的是“一件事”的上下文、状态和流程，谁来做不是关注点，不建立公司体系的角色。工作流和常用的项目组合做成可分享的文件。（取代同日早先的“先服务个人”。）

**草案**：用 AI Agent 做持续工程化开发的人。他们的任务常常跨多个仓库、跨多个会话，并且需要遵循一定的流程。

一次性的探索式开发和单仓库小改动不是首要服务对象：Atrium 对它们无害，但也带不来多少价值。

## 三大能力

### 上下文环境

**已确认**：

- 一个任务对应一个空间，并行靠多开空间。
- 空间由项目组成。项目就是 Git 仓库或文档目录，知识库也是普通项目，用途靠说明区分。
- 集中存储空间的元数据，磁盘上的空间是它的实例。组合以元数据为准；分支和改动实时读磁盘，不写入元数据。

**草案**：

- 每个项目记录三样东西：来源、接入方式（为这个任务开分支、固定在某个提交作参考、映射共享目录）和用途说明。
- 磁盘上的实例包括：项目目录，以及由元数据生成的 Agent 说明文件（如 `AGENTS.md`）和编辑器工作区文件。Agent 和编辑器从空间根目录打开，就能直接看到全部项目。
- 生命周期：创建、调整成员、回收（保留元数据和历史）、按元数据重建、导出与导入。回收和重建前有未提交或未推送的改动时拦住（已确认，见非目标第 5 条）。
- 跨空间总览：所有空间各在做什么、各项目处在哪个分支、有没有未提交或未推送的改动。

### 任务状态

**已确认**：大任务需要跨会话追踪状态；一个空间只有一个当前任务。

**已确认（2026-10-20）**：任务与空间是同级的两个体系，任务不属于某个空间目录。

- 任务记录需要哪些项目，以及从哪个空间产生（来源空间）；登记时可以只记一部分。
- 任务的产生方式不止 backlog：直接开始、先记下以后做、暂停、从别的任务拆出、从对话中捕获；产生时都不要求先确定空间。
- 内置 Agent 可以在对话中登记任务。
- 开始任务时三种去处：回到来源空间；照来源空间的组合新开空间；根据任务的项目需求反向创建空间。反向创建先展示可编辑清单，不直接实例化。
- 开始后基本固定在一个空间做完；只有“暂停后原空间被占用”时才到新空间继续，且要求改动已提交。

**草案**：

- 任务记录目标、关键决策、进度、下一步和相关资料，新会话进入空间时可以恢复。
- 跨空间查找任务。
- 任务状态只做索引和进度，长期的设计和讨论放在项目里（例如知识库），不在任务状态里复制。

### 工作流

**已确认**：工作流定义任务怎么执行，是扩展点。插件机制按通用方式设计，不局限于工作流；首期交付哪些扩展点，划 MVP 时再定。见[扩展机制](extensions.md)。

**已确认（2026-10-20）**：

- 默认工作流以官方工作流包提供：核心不含流程内容，官方包按普通插件安装、默认启用，可以停用并换成自己的工作流。
- spec、Review 等是工作流的产物，挂在任务上：工作流声明每一步产出或依赖哪些产物；任务记录产物及其状态（草案、已确认、通过、要返修），由程序维护，闸门据此判断能否推进；正文用 Markdown，跟着任务存放和归档，有长期价值的结论在收尾时提炼到项目里。核心不写死 spec、Review 这类概念。
- 任务可以不使用工作流，只做状态追踪；这个选择必须由用户明确做出，Agent 不能替用户决定。

**草案**：工作流规定一类任务的步骤、闸门和完成条件；任务记录自己用的是哪个工作流、走到了哪一步。

## 三者的关系

**草案**：

```text
空间（在哪做） ──承载──▶ 当前任务（做到哪） ──遵循──▶ 工作流（怎么做）
```

Agent 打开一个空间时，能同时拿到三样东西：这件事涉及的项目、当前进度，以及接下来应该遵循的流程。三者由同一份结构化状态联动：任务开始时，空间的说明文件会反映它；通过 Atrium 接口推进任务时，工作流的闸门会拒绝越过当前步骤的操作。任务也可以不使用工作流，只追踪状态。

## 贯穿所有能力的部分

**已确认**：入口包括桌面端、CLI、外部 Agent 和内置 Agent；状态由程序维护；Agent 接入作为贯穿问题单独考虑。

**已确认（2026-10-20）**：内置 Agent 只做组织类工作（建空间、登记和管理任务、推进流程）；业务编码交给外部 Agent，调度外部 Agent 暂不做。

**草案**：

- **入口**：
  - 桌面端：可视化查看、直接操作和自然语言交互。
  - CLI：确定性命令和交互式 Agent 模式。
  - 外部 Agent：通过 Skill 或接口调用。
  - 确定性的操作可以直接执行，不必经过 Agent；Agent 处理意图不明确的请求。
- **Agent 接入**：Agent 进入空间时，能可靠地知道这是 Atrium 空间、当前任务是什么、该通过什么接口操作，而不依赖 Agent 是否“记得”去加载某段规则。
- **状态与操作接口**：任务、空间、工作流的状态以结构化数据保存，所有修改都通过明确的操作完成。Markdown 用于说明和展示。
- **授权护栏**：Atrium 自身有副作用的操作（回收、重建、删除，以及越过工作流闸门）必须有用户的真实确认，Agent 不能自己给自己授权。护栏只拦真正有风险的操作，不给日常操作增加负担。
  - **候选**（来自现行 Skill 的使用经验，后续可能调整）：护栏由程序在核心操作中执行，不靠 Skill 文字规则。外部 Agent 有自己的 shell，可以绕过 Atrium 直接改文件或执行 git；Atrium 只能管住经过自身接口的操作，需要写明能保证到什么程度，不宣称“强制拦截”。

## 与现有工具的关系

**草案**：

- Agent 工具（Claude Code、Codex 等）负责理解和执行，Atrium 为它们准备环境、保存状态、约束流程，不替代它们。
- Git 和编辑器负责代码版本和编辑。Atrium 读取 Git 状态，也会建立分支和工作目录，但不提供提交、对比、合并等日常 Git 操作。
- 规则内容（编码规范、分支策略等）和知识库内容由各自的仓库维护，Atrium 不管理这些内容。

## 非目标

**已确认（2026-10-20）**：

不做（产品边界）：

1. 不做编码 Agent。业务编码交给 Claude Code、Codex 等工具，内置 Agent 只做组织类工作。
2. 不做编辑器，也不做 Git 客户端的日常操作。Atrium 会建分支和 worktree、读取 Git 状态；提交、对比、合并、解决冲突留在 Git 和编辑器里。
3. 不管理知识库和团队规则的内容。它们是空间里的普通项目；“哪类任务要带哪些项目”由插件或团队规则提供。
4. 不做通用的 Agent 平台或自动化平台。Agent 能力只围绕空间、任务和工作流。
5. 不备份代码。重建只恢复工作环境。回收和重建前，任何成员存在未提交或未推送的改动时直接拦住，不执行。
6. 不做严格的期望状态收敛。发现磁盘与元数据不一致时提示用户，由用户决定，不自动改回。

首期不做（以后可能做）：

7. 账号、角色和权限体系，以及持续同步服务。仓库访问权限由 Git 托管平台等外部系统负责；跨机器恢复见[上下文环境](context-environment.md)“导出与导入”。
8. 调度外部 Agent，等有明确场景再讨论。
9. 不把一次性、单仓库的小改动作为首要场景；不妨碍这类用法，但不专门优化。

**待讨论**：被拦住后的处理方式，例如先提交推送，或用户明确选择放弃改动后再执行；放弃改动属于授权护栏的范围。
