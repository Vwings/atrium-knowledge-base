# 任务与工作流

## 状态

汇总“任务状态”和“工作流”两项能力的讨论结论和候选设计。已确认结论按主题汇总在 [README](../README.md)。

## 任务状态

**已确认（2026-10-20 用户陈述）**：超大的任务不可能一个会话完成，需要追踪任务状态的机制，这是 Atrium task 做的事。

**已确认（2026-10-20）**：一个空间一个 current，并行靠多开空间。理由是：

- 工作树隔离：一个空间里的项目只服务一件事，改动不互相干扰；
- 上下文不含糊：Agent 进入空间就知道当前在做什么；
- 授权范围明确；
- 心智模型简单。

stash 只处理临时打断，不承担并行。

**倾向**：状态由程序维护、以结构化数据作为事实来源，所有修改通过明确的操作接口完成，避免 Agent 直接编辑 Markdown 的 frontmatter、标题和 checkbox 后再靠脚本补救。Markdown 用于设计说明、过程记录和人类阅读；是否由结构化状态渲染生成，按文档类型分别决定。存储形式未选。

**候选**：任务状态只做索引和进度（目标、关键决策、进度、下一步、相关资料），长期的设计和讨论放在项目里，不在任务状态里复制。依据：现行 Skill 的 current.md 曾累积大段架构参考和材料清单，与知识库重复且摘要落后。

spec、Review 等任务资料的归属见下文“工作流”：它们是工作流的产物。

## 任务与空间的关系

**已确认（2026-10-20）**：任务与空间是同级的两个体系，都集中存储，靠关系相连，谁也不拥有谁。现行 Skill 把任务放在空间目录下，是因为它只有文件、没有集中存储，不是产品必须如此。

```text
空间 ──current（最多一个）──▶ 任务 ──采用──▶ 工作流定义
  │                             │
  └── 项目成员                  └── 运行实例（流程走到哪一步）
```

- **产生**：任务的产生方式不止 backlog，还有直接开始、暂停（stash）、从别的任务拆出、从对话中捕获。产生时都不要求先确定属于哪个空间、放在哪个目录。内置 Agent 可以在对话中识别并登记任务，登记走核心操作；外部 Agent 也可以通过 CLI 做同样的事。
- **项目需求**：任务记录需要哪些上下文，即涉及哪些项目，知道时再记角色和基线（例如“改 SDK 主线，参考旧定制版 v3.2，需要测试宿主”）。空间记录的是这些需求实际落成的 worktree 和链接。登记时可以只记一部分，开始时再补；内置 Agent 可以从对话或来源空间推断候选。
- **来源空间**：从某个空间产生的任务记录来源空间，作为开始时的默认推荐，不表示归属。
- **开始时的三种去处**：

  | 情况 | 推荐动作 |
  | --- | --- |
  | 来源空间空闲，组合满足需要 | 回到来源空间，设为 current |
  | 来源空间正在做别的事 | 用来源空间的组合加任务的项目需求，新开空间 |
  | 没有来源空间，或项目差别较大 | 按任务的项目需求生成空间计划，在可编辑清单中调整后实例化 |

  登记时记的项目需求可能不准或过时，反向创建先展示清单，不直接实例化。
- **开始后**：任务基本固定在一个空间做完，因为进度落在该空间的 worktree 里（未提交改动、本地分支）。只有“暂停后原空间被占用”时才到新空间继续，用同一分支接着做，要求改动已提交。空间回收后按元数据重建不算换空间；范围变化应调整原空间成员；还没开始的任务换空间只是改推荐，不算“用过”。不把“任务先后用过多个空间”作为专门设计的能力。

## 任务与工作流的关系

**候选**（2026-09-22 提出，未确认）：

| 概念 | 回答的问题 | 候选职责 |
| --- | --- | --- |
| 任务 Task | 要完成什么？ | 目标、范围、状态、关联项目和成果；创建时不要求已有工作流或 Agent 对话。 |
| 工作流定义 | 按什么步骤和规则推进？ | 可复用的步骤、推进条件和规则，可由插件提供；不绑定某个任务的进度。 |
| 工作流运行实例 Run | 某次流程实际推进到了哪里？ | 某任务采用某工作流后的步骤进度、等待、结果与历史；是业务记录，不等于进程或 Agent 对话。 |

- 一个任务可以涉及多个项目，也可以暂时没有关联项目，例如尚在澄清的想法。
- 一份工作流定义可复用于多个任务；同一任务可以先后形成多个运行实例，例如需求分析、开发和发布。是否支持并行流程、子流程和跨任务流程待场景验证。
- 工作流步骤可以由人、外部 Agent、内置 Agent 或程序完成。核心记录并校验推进条件，不把一次脚本成功直接等同于任务完成。
- Agent 对话可以关联任务或运行实例；结束对话不自动结束任务或流程。

Task 与 Run 分离是新提出的候选设计；早期工作方式把 Task 视为工作流的运行实例。需要用切换流程、保留历史等场景判断是否值得引入独立对象。

场景验证（“增加一项能力，需要修改产品代码和文档”）：先登记任务，此时可以未选空间和工作流 → 选择或创建空间，加入代码项目和文档项目，任务进入该空间 → 选择需求分析工作流，形成运行实例 → 进入开发时形成新的运行实例，继续关联同一任务 → 人、CLI、桌面或 Agent 通过核心查询和推进状态，任务成果与对话记录分别保留。

## 工作流

**已确认（2026-10-20 用户陈述）**：工作流定义任务怎么执行。光有进度不够，任务还要按有效的规范流程执行；不同公司可能有专属流程，工作流作为扩展点。

**已确认（2026-10-20）**：工作流是用户能力之一，与上下文环境、任务状态并列；它的主次和首期程度留到 MVP 阶段决定。

**已确认（2026-10-20）**：

- 默认工作流以官方工作流包提供：核心不含流程内容，官方包按普通插件安装、默认启用，可以停用并换成自己的工作流。
- spec、Review 等是工作流的产物，挂在任务上：工作流声明每一步产出或依赖哪些产物；任务记录产物及其状态（草案、已确认、通过、要返修），由程序维护，闸门据此判断能否推进；正文用 Markdown，跟着任务存放和归档，有长期价值的结论在收尾时提炼到项目里。核心不写死 spec、Review 这类概念。
- 任务可以不使用工作流，只做状态追踪；这个选择必须由用户明确做出，Agent 不能替用户决定。

不同工作流的产物各不相同：需求分析产出结论，开发产出 spec 和 Review，提测工作流产出提测单。官方包也走插件机制，正好检验机制是否够用。Review 要求返修这类改变闸门的状态变更，需要用户的真实确认。

**候选**：

- 工作流规定一类任务的步骤、闸门和完成条件；任务记录用的是哪个工作流、走到了哪一步。
- 官方工作流包的内容可以来自现行 Skill 中实际用过的工作流（需求分析、开发、修 Bug 等）。插件的声明、边界、版本和冲突处理按通用插件机制设计，见[扩展机制](extensions.md)。
- 支持非线性推进，例如以议题或决策项为单位循环，阶段只作为出口条件。
- 确认强度按仓库、目录或产物类型可配置，由程序判定。
