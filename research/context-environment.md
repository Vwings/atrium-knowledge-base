# 上下文环境（空间）

## 状态

汇总“上下文环境”能力的讨论结论和候选设计。结论分级为已确认、倾向、候选、否决；已确认结论的原话与日期另汇总在 [README](../README.md)。产品全貌中的位置见[产品全貌草案](product-overview-draft.md)。

## 为什么需要空间

**已确认（2026-10-20 用户陈述）**：用 AI 开发，首先要打开一个文件夹。文件夹下有什么，直接影响 Agent 能看到什么；Agent 能自己找，但不如东西就在眼前。`/add-dir` 之类的命令不太好用。人也需要用编辑器查看任务相关的项目。空间的初衷是为一个任务快速准备好必要的上下文，人机都友好。

**已确认（2026-10-20）**：

- 一个空间一个 current，并行靠多开空间。
- 不直接用 worktree，是因为复杂任务往往涉及多个 Git 仓库，单个仓库描述不了一件事。
- “空间等价于 worktree”是用户给出的概念类比，说明空间为一件事提供隔离的工作环境；它不是定义，不能据此推导空间必须具备 worktree 的全部语义。
- 目标是让开空间、开任务、跨空间找任务、找仓库池、操作空间内项目状态都成为随手的事。可靠性与授权是“随手”成立的前提，不是核心价值本身：确定操作由程序直接执行才快，结果确定才不必盯着 Agent，授权护栏不能给随手操作增加负担。

一空间一 current 的理由见[任务与工作流](task-and-workflow.md)。

## 空间成员

**已确认（2026-10-20）**：空间成员只有“项目”一个通用概念。项目就是 Git 仓库或文档目录；知识库也是普通项目，不作为一等公民，用途靠说明区分。哪类任务需要带哪些项目，属于团队规则或扩展，不进 Atrium 核心。

### 项目来源与接入方式

**已确认（2026-09-22）**：沿用用户一直使用的实践：

| 用途 | 来源与接入方式 | 必须保留的区别 |
| --- | --- | --- |
| 交付、配套项目及测试宿主 | 从裸仓库池创建关联实际分支的 worktree | 共享仓库数据，工作目录及未提交修改独立；需检查分支和工作目录占用。 |
| 定制版、历史版本及其他端参考实现 | 从裸仓库池创建固定提交的 detached worktree | 同一仓库可同时出现目标分支和参考提交；基线必须明确。 |
| 知识库及按需加入的共享项目 | 从共享目录池通过 Junction、symlink 等映射进入空间 | 多个入口访问同一工作副本，修改会影响共享目标；映射不提供隔离。 |

确认范围是这套来源与接入方式，不排除其他接入方式；`_bare`、`_share` 只是目录约定。固定提交和 detached 状态不强制只读，目录映射也不代表只读；“只读参考”是使用约定。具体界面、自动化程度、跨平台实现和资源生命周期仍待设计；是否支持普通 clone 加 linked worktree、如何接管现有目录，待讨论。

### 成员配置

**候选**：同一项目在不同空间、甚至同一空间里可以承担不同角色，例如同一 SDK 仓库一份是待修改的主线工作目录，一份是固定旧提交的参考目录。任务只关联“SDK 项目”不足以表达操作对象，需要记录成员配置：

- 用途：交付、配套、测试、参考等；
- 基线：分支或固定提交；
- 接入方式：分支 worktree、固定提交 worktree、共享映射、已有目录；
- 路径：空间内入口与真实目标；
- 访问约定：可修改、参考只读等；
- 管理责任：Atrium 创建的资源，还是仅登记的外部资源。用于区分移除成员关系、移除映射、回收工作目录和删除原始资源。

**候选**：说明资料分两层。项目的通用简介回答“这个项目做什么”，可跨空间复用；成员的空间内角色回答“这次为什么加入、承担什么用途”，由本次工作决定。Agent 可以从仓库资料草拟简介并保留来源，缺少可靠信息时提示待补充；不要求入池前全部手写，也不把草拟内容视为已核实事实。

## 元数据与磁盘实例

**已确认（2026-10-20）**：集中存储一份空间元数据，磁盘上的空间是它的实例。

- 元数据：身份与用途、成员组合（来源仓库与接入方式）、目标分支与固定提交、用于生成 `AGENTS.md` 的上下文、任务状态和生命周期。版本化、审计和重建由元数据承担。
- 实例：目录、worktree、链接，以及生成的 `AGENTS.md`、`.code-workspace`；可以回收和重新生成。

**已确认（2026-10-20）**：组合以元数据为准，分支和改动读磁盘。

- Git 当前分支、未提交与未推送改动实时从磁盘读取，不存入元数据；手动切分支或提交不算偏离。
- 发现组合不一致（例如手动加入的仓库目录）时提示用户，由用户选择收进元数据或忽略。
- 不采用 Terraform、Kubernetes 式的严格期望状态收敛。

**否决（2026-10-20）**：把空间目录本身做成 Git 仓库。理由：根目录成为仓库后，Agent 和编辑器容易操作到错误的仓库；每个一次性空间各自成为仓库，与随手开收冲突，回收后历史无处安放；全局视图仍需集中索引。

**待讨论**：空间目录如何自我说明。候选是只放生成的 `AGENTS.md` 和小标记文件，状态不放在目录内。

## 生命周期

**候选**：两层划分带来的操作：

- 创建：写元数据，再实例化；
- 调整：增删成员、改变成员角色、重新生成说明文件；
- 以已有组合为模板复用；
- 回收：回收实例，保留元数据和历史；
- 重建：按元数据重新实例化；
- 核对：元数据与磁盘是否一致；
- 跨空间总览：各空间在做什么、项目在哪个分支、有无未提交和未推送改动。

### 导出与导入

**已确认（2026-10-20 用户设想）**：在一台机器上做到一半，到另一台机器能接着做。方式是导出一个描述文件，另一台机器 `atrium import` 后恢复整个工作环境；各项目按记录的 Git 地址直接拉取重建。不需要服务器，也不做持续同步。

优先级不高，细节到做的时候再展开。已讨论到的要点（候选）：描述文件记录项目的 Git 地址、分支或基线、接入方式和任务状态，不写本机路径；导出前存在未提交或未推送改动时拦住；不是 Git 仓库的文档目录无法拉取，需要标出。

### 重建的限制

**候选**：重建只恢复工作环境，不代替提交和推送。

- 未提交的改动无法恢复。
- 同机误删目录时，已提交未推送的提交仍在裸仓库中，可以恢复；需要先清理失效的 worktree 登记。
- 换机重建只能恢复已推送的内容，并依赖目标机器的共享池与 Atrium 状态同步。
- **已确认（2026-10-20）**：回收和重建前，任何成员存在未提交或未推送的改动时直接拦住，不执行。总览中标出有风险的空间。绕过 Atrium 直接删除目录造成的损失无法挽回。

## 创建体验

**候选**：创建、调整这类组合多个资源的操作，以自然语言配合可直接编辑的资源清单为主要入口之一。简单的改名、增删已知项目、选择确定版本可以直接操作；常用组合可以复用。

纯命令行太费时；纯 UI 要求用户逐项搜索项目池、选分支或 tag、决定接入方式，同样变成大量点击；Agent 加 Skill 减少了操作，但执行过程不可见、结果不可信。因此“程序化”不等于“不需要 Agent”，而是分工：

- **程序确定性完成**：发现项目池、共享目录池和已有资源；识别分支、tag、commit、worktree 和链接；检查路径、版本、分支占用、目标存在性和权限；按已确认计划创建或复用资源；记录每个动作的结果和错误；验证实际目录、基线、链接目标与元数据一致。
- **需要语义理解或人确认**：从“准备一个 SDK 迁移空间”判断需要哪些项目和角色；解释项目为何相关；资料不足时补足说明；在多个合理组合之间取舍。

### 示例：准备 SDK 迁移空间

用户输入：“我要把旧定制版的一项能力迁到当前 SDK，帮我准备空间，带上测试宿主和知识库。”

这可以作为对话起点，但不足以直接创建。系统有可信的项目和任务上下文时可以提出有依据的候选；没有依据就澄清具体对象，不能根据“SDK”猜定仓库和版本。缺失信息标为待补充，推测标为建议。用户已给出明确的项目、版本和共享目录时，即使还没有具体任务，也可以准备空间。

1. 查询已登记的项目来源、简介与可用版本；Agent 可以在允许范围内读取 README 等资料。只澄清影响结果的项目或版本，不逐个询问能由现有配置确定的字段。
2. 展示一份可修改的资源清单：目标 SDK 的分支 worktree、旧版固定提交参考、测试宿主、共享知识库；每项显示来源、用途、目标位置和待解决的问题。
3. 用户可以直接改清单，也可以说“参考改成另一个版本”；两种操作更新同一份草案。人工调整要保留，Agent 后续修改要显式展示。
4. 程序校验并执行已授权的操作，逐项显示结果；冲突时给出具体处理选项。只在首次执行或授权范围变化时确认，不把每个内部步骤变成一次审批。
5. 根据实际结果和项目说明生成 `AGENTS.md`。

判断是否解决了问题：用户不必手写 Git 和链接命令，也不必重复逐项选择常用资源；能看清最终组合和实际结果并局部修改，而不是只得到一段聊天总结；缺少简介时可以由 Agent 辅助提取，生成后可纠正和复用；失败后明确已完成和未完成项，不重复创建已成功的资源。

### 计划、执行与部分失败

**候选**：

- 用户只说“用最新主线”“参考旧版本”时，系统要解析成具体的远端引用或提交，并在计划中展示；无法唯一解析时澄清，不静默猜测。
- 计划至少列出：目标路径、项目角色、来源、分支或提交、接入方式、是否共享、可能覆盖的文件、失败后的清理范围。确认粒度允许只批准资源准备，不同时批准任务启动或代码修改。
- 多项目创建不是不可分割的黑盒。每个资源有明确结果（如已计划、已复用、已创建、已跳过、失败），并记录来源、路径和错误；部分失败时保留已成功资源的事实，提供继续、重试、调整或清理。
- 回滚按管理责任处理：本次新建的 worktree 可以回收；用户原有目录、裸仓库和共享目标不能因为本次失败而删除。是否自动回收新建资源，待定。
- 创建完成后的增删项目、切换参考提交都是显式变更；重复执行同一计划要有明确的复用或冲突语义。创建空间不等于开始某个任务。

“所有有副作用的操作统一预览再确认”的早期提议未获批准；已有明确授权应复用。

## `AGENTS.md` 生成

**候选**：`AGENTS.md` 保持简短，优先写项目职责、目录和必要的规则入口；分支、提交和运行状态这类易变事实留在元数据和详情界面，不在说明中重复。

- 稳定部分由程序根据元数据生成：空间名称、目录地图、项目角色、入口路径、来源和访问约定，不依赖 LLM。
- 语义部分（项目做什么、这次为什么加入）来自项目简介和成员角色；缺少时由 Agent 草拟，带来源，随整份清单审阅，不默认强制逐条确认。
- 没有 Agent 时，仍能生成可用但较简略的 `AGENTS.md`。

`.code-workspace` 等编辑器文件同理由元数据生成；不把 VS Code 绑定为唯一入口。

## 待讨论

- 空间目录如何自我说明（见上）。
- 空间根目录下不属于任何项目的文件：用户自己加的笔记、脚本、临时文件，以及被手工改过的生成文件（`AGENTS.md`、`.code-workspace`）。它们不在任何 Git 仓库里，回收、重建、导出时既不会被检查出未提交，也无法从远端恢复。2026-10-20 用户提出需要考虑，处理方式待讨论。
- 资源池能力：登记和发现仓库池、共享目录池，按需 fetch，查看仓库分支及被哪些空间使用。
- “一句描述开空间”时由 Agent 推断所需项目，算开空间的一部分还是 Agent 的独立能力。
